Q1. What is SynergyAI?
─────────────────────
SynergyAI is an enterprise-grade Mergers and Acquisitions (M&A) platform that
automates deal sourcing, streamlines due diligence, and generates deep financial
intelligence using AI. It combines a Next.js 15 frontend with a FastAPI backend,
leveraging local LLMs (via Ollama), RAG (Retrieval-Augmented Generation) with
FAISS vector search, Redis caching, and a PostgreSQL database (via Supabase).

It provides features like:
- AI-powered deal sourcing with strategic fit scoring
- Virtual Data Room (VDR) with semantic search
- One-click investment memo generation
- Monte Carlo valuation simulations
- Corporate knowledge graph visualization
- Risk and synergy scoring
- Role-based access control (RBAC)


Q2. Why did you build SynergyAI?
─────────────────────────────────
M&A is one of the most complex, data-intensive domains in finance. Investment
bankers, analysts, and private equity firms spend weeks manually reviewing
thousands of pages of documents, calculating valuations, and writing investment
memos. SynergyAI was built to:
1. Automate repetitive M&A workflows using AI
2. Demonstrate a production-grade full-stack AI application
3. Showcase integration of local LLMs, RAG pipelines, and real-time caching
4. Provide a scalable, multi-user, multi-tenant collaboration platform


Q3. What problem does it solve?
───────────────────────────────
- Manual due diligence is slow: analysts read 1000+ pages of documents
- Valuation modeling is error-prone and siloed
- Risk identification is subjective without AI pattern recognition
- Collaboration is fragmented across email, spreadsheets, and file shares
- Confidential data leaks via cloud-based AI APIs

SynergyAI solves these by:
  Using RAG to let users "chat" with their documents
  Auto-generating risk profiles, synergy scores, and investment memos
  Running all AI locally (Ollama) so no data leaves the infrastructure
  Providing project-level data isolation and RBAC


Q4. Who are the intended users?
───────────────────────────────
- Investment Bankers conducting M&A advisory
- Private Equity analysts performing due diligence
- Corporate Development teams evaluating acquisition targets
- Analysts performing financial modeling and risk assessment
- Fund managers overseeing deal pipelines

RBAC roles in the system:
  Admin    -> Full project control, manage members, delete projects
  Editor   -> Can modify project data, upload documents, run AI analyses
  Viewer   -> Read-only access to project dashboards


Q5. Why is M&A a good use case for AI?
───────────────────────────────────────
M&A involves:
1. Massive unstructured data (legal contracts, financial reports, SEC filings)
2. Pattern recognition (risk identification across thousands of clauses)
3. Quantitative modeling (valuations, Monte Carlo simulations)
4. Natural language understanding (summarizing complex documents)
5. Time pressure (deals have strict deadlines)

AI excels at all five. LLMs can summarize 100-page contracts in seconds.
Vector search finds relevant clauses across gigabytes of documents instantly.
This makes M&A one of the highest-ROI verticals for AI automation.


Q6. What makes SynergyAI different from a normal chatbot?
─────────────────────────────────────────────────────────
A normal chatbot is a single-turn Q&A interface. SynergyAI is fundamentally
different:

Feature               | Normal Chatbot   | SynergyAI
──────────────────────|──────────────────|────────────────────────────
Data Source           | Training data    | User's own VDR documents
Architecture          | API call to GPT  | Local LLM + RAG + FAISS
Output                | Text response    | Structured JSON, scores, PDFs, reports
Multi-user            | No               | Yes, with RBAC + RLS
Domain Knowledge      | Generic          | Fine-tuned for M&A
Data Privacy          | Cloud-dependent  | 100% local inference
Caching               | None             | Redis + hover-to-predict
Financial Modeling    | None             | Monte Carlo, DCF, Comps

How does frontend communicate with backend?
───────────────────────────────────────────
1. Frontend uses standard HTTP fetch() calls to FastAPI REST endpoints
2. Every request includes Authorization: Bearer <jwt_token> header
3. The JWT token comes from Supabase Auth (stored in cookies via @supabase/ssr)
4. FastAPI validates the JWT using supabase.auth.get_user(token) in security.py
5. For streaming (deal sourcing), SSE via StreamingResponse is used
6. Frontend also directly queries Supabase for auth state (e.g., getUser())

Flow:
  User Login -> Supabase Auth -> JWT stored in cookie
                                        |
  Dashboard Load -> fetch('/api/dashboard/narrative', {
                      headers: { Authorization: `Bearer ${jwt}` }
                    })
                                        |
  FastAPI -> get_current_user_id() -> supabase.auth.get_user(token)
                                        |
  If valid -> proceed to route handler -> query Supabase DB -> return JSON

Why did you choose Next.js?
───────────────────────────
1. Server-Side Rendering (SSR) for SEO and faster initial page loads
2. App Router (Next.js 15) for file-based routing
3. Built-in API routes (though we use FastAPI as the primary backend)
4. Excellent React ecosystem: Shadcn UI, Radix, Tanstack Query
5. Middleware support for authentication guards (src/lib/middleware.ts)
   Redirects unauthenticated users away from /dashboard/* routes
6. TypeScript support for type safety
7. Our frontend uses: React 19, Tailwind CSS, Zustand (state), ECharts,
   Recharts, jsPDF, react-dropzone, react-markdown, @hello-pangea/dnd (Kanban)


Q13. Why FastAPI instead of Node.js/Express?
────────────────────────────────────────────
1. Python is the lingua franca of AI/ML: all our AI libraries
   (FAISS, sentence-transformers, numpy, reportlab) are Python-native
2. FastAPI has native async/await support: critical for our parallel
   LLM calls using asyncio.gather()
3. Automatic request validation via Pydantic models
4. Auto-generated OpenAPI documentation
5. Dependency injection for auth: user_id: str = Depends(get_current_user_id)
6. We fire 5+ concurrent Ollama prompts per request: Python asyncio handles
   this naturally without callback hell

If we used Express, we would need Python microservices anyway for FAISS +
sentence-transformers, adding unnecessary network hops and complexity.


Q14. Why PostgreSQL?
────────────────────
1. M&A data is highly relational:
   projects -> project_members -> users
   projects -> vdr_documents -> document_annotations
   companies -> executive_roles -> executives
   companies -> company_relationships
   projects -> project_tasks, valuation_simulations, etc.
2. ACID compliance for financial data
3. Support for JSONB columns (financial_summary, industry)
4. pgvector extension for potential embedded vector search
5. Row Level Security (RLS) for multi-tenant data isolation
6. Foreign key constraints prevent orphaned data


Q15. Why Supabase?
──────────────────
Supabase provides a complete backend-as-a-service:
1. PostgreSQL database with RLS
2. Built-in Auth (email/password, OAuth)
3. Realtime subscriptions
4. Auto-generated REST API
5. Storage for files
6. Dashboard for database management

We use it because it eliminates boilerplate: auth, user management,
database provisioning, and RLS are all pre-configured.


Q16. What does Supabase actually provide?
─────────────────────────────────────────
In our app specifically:
  Authentication: sign_up(), sign_in_with_password(), get_user()
  Database: PostgreSQL with tables for users, projects, companies, etc.
  RPC Functions: get_user_projects, get_project_team_members,
                  get_categories_with_counts, create_project_and_add_members
  Row Level Security: Project-level data isolation
  Client Libraries: @supabase/supabase-js (frontend), supabase-py (backend)

Backend uses: Service Role Key (bypasses RLS for admin operations)
Frontend uses: Anon Key (respects RLS)


Why not use MongoDB?
────────────────────
MongoDB is document-based (NoSQL). M&A data is inherently relational:
  A project has members (many-to-many via project_members)
  A company has executives via executive_roles (join table)
  Documents belong to projects, annotations belong to documents
  Tasks reference projects AND users

With MongoDB, you'd either:
1. Embed everything -> massive document bloat, update anomalies
2. Reference manually -> losing all relational guarantees

PostgreSQL gives us:
  JOINs for complex queries (knowledge graph, team + role lookups)
  Foreign keys for referential integrity
  JSONB for semi-structured data (financial_summary, industry)
  RLS for security
  Strong consistency (ACID)


Q18. Why use a relational database for M&A?
───────────────────────────────────────────
M&A entities have strict relationships:
  Company -> has many Executives (via executive_roles)
  Company -> has many Relationships (subsidiaries, competitors)
  Project -> belongs to a Company (via company_cin)
  Project -> has many Members (via project_members with roles)
  Project -> has many VDR Documents
  Document -> has many Annotations
  User -> can be in many Projects with different roles

This is a classic relational schema. Using NoSQL here would be an
anti-pattern: you'd lose JOIN capability, referential integrity,
and RLS-based security.

How do you handle errors?
─────────────────────────
1. Every endpoint is wrapped in try/except
2. HTTPException with proper status codes:
   400: Bad request (invalid input)
   401: Not authenticated (invalid/missing JWT)
   403: Forbidden (not a project member, not an admin)
   404: Resource not found
   500: Internal server error
3. Graceful AI fallbacks: if Ollama is down, pre-written fallback content
   is returned (see prompt_templates.py)
4. OOM protection: if parallel LLM calls cause Out-of-Memory, the system
   catches the error and returns a degraded response

Example from ai.py:
  except httpx.RequestError:
      return {"answer": "AI service is currently unreachable.", "sources": []}
  except httpx.HTTPStatusError:
      return {"answer": "AI model encountered OOM error.", "sources": []}

Q26. How do you handle authentication?
──────────────────────────────────────
1. User signs up/logs in via /api/auth/signup or /api/auth/login
2. These call Supabase Auth: supabase.auth.sign_up() / sign_in_with_password()
3. Supabase returns a JWT token (session)
4. Frontend stores the JWT in cookies via @supabase/ssr
5. Every subsequent API call includes: Authorization: Bearer <jwt>
6. Backend extracts and validates the token:

   async def get_current_user_id(request: Request) -> str:
       token = request.headers.get("Authorization").split(" ")[-1]
       user_res = supabase.auth.get_user(token)
       return user_res.user.id

This is a FastAPI Dependency: injected into every protected route:
   async def get_projects(user_id: str = Depends(get_current_user_id)):

Additionally, the Next.js middleware (src/lib/middleware.ts) checks
auth on the frontend side and redirects unauthenticated users away
from /dashboard/* routes.


Q27. How do you handle authorization?
─────────────────────────────────────
Three levels of authorization:

Level 1: Authentication (get_current_user_id)
  Is the user logged in? Valid JWT?

Level 2: Project Membership (get_project_member_auth)
  Is this user a member of this project?
  Queries project_members table for user_id + project_id

Level 3: Admin Authorization (get_project_admin_auth)
  Is this user an ADMIN of this project?
  Same query but checks role == 'Admin'

Usage in routes:
  # Any authenticated user
  user_id: str = Depends(get_current_user_id)

  # Only project members
  user_id: str = Depends(get_project_member_auth)

  # Only project admins
  admin_id: str = Depends(get_project_admin_auth)

Admin-only operations:
  Archive project
  Delete project (requires name confirmation)
  Manage team members

Why Supabase?
─────────────
See Q15 above. Key reason: it bundles PostgreSQL + Auth + RLS into
one managed service, eliminating weeks of boilerplate.


Is Supabase a database?
───────────────────────
Supabase IS a PostgreSQL database, but it's more than that. It's a
Backend-as-a-Service (BaaS) that wraps PostgreSQL with:
  Auth layer (JWT-based)
  REST API auto-generation (PostgREST)
  Realtime engine
  Edge Functions
  Storage
  Dashboard/Admin UI


How did you implement authentication?
─────────────────────────────────────
Backend (auth.py):
  POST /api/auth/signup -> supabase.auth.sign_up({email, password, options})
  POST /api/auth/login  -> supabase.auth.sign_in_with_password({email, password})

Frontend (supabaseClient.ts):
  const supabase = createClient(supabaseUrl, supabaseAnonKey)

Middleware (middleware.ts):
  const { data: { user } } = await supabase.auth.getUser()
  if (!user && path.startsWith('/dashboard')) -> redirect to '/'


Q77. What is Row Level Security?
────────────────────────────────
RLS is a PostgreSQL feature where access policies are defined at the
DATABASE level. Even if someone has the SQL credentials, they can only
see rows they're authorized to access.

Example policy:
  CREATE POLICY "Users can view their own projects"
  ON projects
  FOR SELECT
  USING (
    id IN (
      SELECT project_id FROM project_members
      WHERE user_id = auth.uid()
    )
  );

This means: even if you query SELECT * FROM projects, you'll ONLY
get projects where you are a member.


Q78. Why is RLS important for your project?
───────────────────────────────────────────
SynergyAI is a multi-tenant M&A platform. Multiple companies use it
simultaneously. If Company A uploads confidential financial documents,
Company B must NEVER see them. RLS enforces this at the database level.

Even if there's a bug in the application code, RLS acts as a last line
of defense: the database itself refuses to return unauthorized rows.


How would you implement project-level data isolation?
─────────────────────────────────────────────────────
1. Every table has a project_id or user_id column
2. RLS policies check auth.uid() against project_members
3. Backend uses service_role key (bypasses RLS) but manually checks:

   async def get_project_member_auth(project_id, user_id):
       res = supabase.table('project_members')
           .select('role')
           .eq('project_id', project_id)
           .eq('user_id', user_id)
           .single().execute()
       if not res.data:
           raise HTTPException(403, "Not a project member")

4. For VDR documents, queries are always scoped:
   supabase.table('vdr_documents').select('*').eq('project_id', project_id)


Q80. Can frontend users bypass RLS?
────────────────────────────────────
No. The frontend uses the ANON key, which has restricted permissions.
RLS policies are enforced server-side by PostgreSQL. The browser cannot
modify SQL queries. It can only call the REST API, which goes through
PostgREST (which enforces RLS) or our FastAPI (which uses service_role
but manually checks permissions).


Q81. What happens if someone directly calls your API?
────────────────────────────────────────────────────
They need a valid Supabase JWT token. Without it:
  get_current_user_id() raises HTTPException(401, "Not authenticated")

With a valid token but wrong project:
  get_project_member_auth() raises HTTPException(403, "Not a member")

With a valid token and correct project but wrong role:
  get_project_admin_auth() raises HTTPException(403, "Not an admin")


Q82. Where should authorization be enforced?
────────────────────────────────────────────
Defense in depth: enforce at EVERY layer:
1. Frontend middleware: Redirect unauthenticated users
2. API layer: FastAPI Depends() validates JWT
3. Business logic: Check project membership/role
4. Database: RLS policies as last line of defense

Our actual implementation enforces at layers 1, 2, and 3.
RLS (layer 4) is configured in Supabase dashboard.

What is RAG?
────────────
Retrieval-Augmented Generation. Instead of relying solely on the LLM's
training data, RAG retrieves relevant documents from a knowledge base
and injects them into the prompt as context. The LLM then generates
answers grounded in actual data.


Why did you need RAG?
─────────────────────
1. LLMs don't know about our users' confidential M&A documents
2. Fine-tuning alone can't give the model document-specific knowledge
3. Documents change frequently: you can't re-train for every upload
4. RAG grounds the LLM's response in factual document content
5. It's critical for due diligence: answers MUST reference actual clauses


Explain your complete RAG pipeline.
───────────────────────────────────

Document Upload -> Text Extraction -> Chunking -> Embedding -> FAISS Index
                                                                    |
User Query -> Embedding -> FAISS Search -> Top-K Chunks -> Prompt -> LLM -> Answer

DETAILED STEP-BY-STEP (from rag_pipeline.py):

Step 1: DOCUMENT INGESTION (ingest_document method)
  File uploaded via POST /api/vdr/documents/upload
  Saved to uploads/{project_id}/{uuid}{extension}
  Background task: rag_system.ingest_document(file_path, filename)

Step 2: TEXT EXTRACTION
  PDF: fitz.open(file_path) -> page.get_text() (PyMuPDF)
  DOCX: docx.Document(file_path) -> paragraph.text
  TXT: open() and read()

Step 3: CHUNKING
  Split text by whitespace into words
  Chunk size: 400 words
  Overlap: 50 words
  Each chunk stored with source filename

Step 4: EMBEDDING
  Model: BAAI/bge-small-en-v1.5 (SentenceTransformer)
  Dimension: 384
  Each chunk -> 384-dimensional vector
  Uses GPU if available (torch.cuda.is_available())

Step 5: INDEXING
  Vectors added to FAISS index
  Chunk metadata added to chunk_map (list of dicts)
  Index persisted to synergyai_index.faiss (~1 GB)
  Map persisted to synergyai_text_map.pkl (~376 MB)
  Thread lock ensures concurrent safety

Step 6: SEARCH (search method)
  User's query -> embedding (384-dim vector)
  FAISS.search(query_embedding, k=5)
  Returns top-K nearest chunks
  Optional: filter by allowed_sources (project-scoped VDR)
  When filtering: search_k = 2000, then post-filter to k results

Step 7: PROMPT CONSTRUCTION
  Retrieved chunks injected into prompt as "Context"
  Format: "Context from VDR Documents:\n{chunks}\n\nQuestion: ...\n\nAnswer:"

Step 8: LLM GENERATION
  Prompt sent to Ollama (localhost:11434/api/generate)
  Model: synergyai-specialist (fine-tuned LLaMA-3.1-8B)
  Response parsed (often JSON extraction via regex)


Why do you chunk documents?
───────────────────────────
1. LLMs have context window limits (LLaMA-3.1 = 128K tokens, but
   practical prompts should be much shorter)
2. Embedding entire documents would dilute semantic meaning
3. Smaller chunks = more precise retrieval
4. Different sections of a document discuss different topics
5. Chunking enables overlapping to catch cross-boundary information


Q87. Why not embed the entire PDF?
──────────────────────────────────
1. A 100-page PDF might be 50,000 words. A single embedding would lose
   all nuance (one 384-dim vector can't capture everything)
2. Retrieval would return the entire document instead of relevant sections
3. LLM context window would overflow
4. Search precision would plummet


How large were your chunks?
───────────────────────────
400 words per chunk. This was chosen because:
  Large enough to contain a complete paragraph or clause
  Small enough to maintain semantic coherence
  Aligned with the embedding model's optimal input length
  ~500-600 tokens per chunk (well within model limits)


Did you use overlapping chunks? / Q90. Why chunk overlap?
─────────────────────────────────────────────────────────
Yes. Overlap = 50 words.

From rag_pipeline.py:
  chunk_size = 400
  overlap = 50
  i = 0
  while i < len(words):
      chunk_words = words[i:i + chunk_size]
      i += chunk_size - overlap  # i += 350

If a critical clause spans the boundary between two chunks, without
overlap it would be split and potentially lost. The 50-word overlap
ensures that boundary content appears in both adjacent chunks.


Q91. What happens if a clause is split across chunks?
────────────────────────────────────────────────────
The 50-word overlap handles most cases. For very long clauses:
1. Both adjacent chunks would contain partial content
2. Top-K retrieval (k=5 or k=10) often retrieves both chunks
3. The LLM sees both and can reconstruct the full meaning


Q92. How would you improve chunking?
────────────────────────────────────
  Use sentence-boundary-aware chunking (spaCy or NLTK)
  Implement section-header-based splitting (detect "Article 1:", etc.)
  Use recursive character text splitting (LangChain style)
  Implement sliding window with dynamic sizing based on document structure
  Add semantic chunking: split at points where topic similarity drops


What is an embedding?
─────────────────────
An embedding is a dense numerical vector that captures the semantic meaning
of text. Text with similar meaning produces vectors that are close together.

"The company's revenue grew 20%" -> [0.12, -0.45, 0.78, ..., 0.33] (384 dims)
"Sales increased by a fifth"     -> [0.11, -0.44, 0.79, ..., 0.32] (similar!)
"The dog sat on the mat"         -> [0.85, 0.22, -0.11, ..., -0.67] (different)


Q94. Why convert text to vectors?
─────────────────────────────────
1. Enables semantic search: find meaning, not just keyword matches
2. "What are the company's liabilities?" matches "The firm owes $5M to..."
3. SQL LIKE can only find exact keyword matches
4. Vectors enable cosine similarity measurement in O(1) per comparison
5. FAISS can search millions of vectors in milliseconds


Q95. What embedding model did you use?
──────────────────────────────────────
BAAI/bge-small-en-v1.5 via SentenceTransformer

From rag_pipeline.py:
  EMBEDDING_MODEL_NAME = 'BAAI/bge-small-en-v1.5'
  self.model = SentenceTransformer(EMBEDDING_MODEL_NAME, device=device)

Why this model:
  Only 130MB (fits easily on any GPU/CPU)
  384-dimensional output (compact, fast to search)
  Top-tier performance on MTEB benchmark for its size
  Excellent for retrieval tasks (what RAG needs)


What is the dimension of your embedding?
────────────────────────────────────────
384 dimensions. Each text chunk is represented as a point in 384-dim space.


Euclidean distance vs cosine similarity?
────────────────────────────────────────
Euclidean distance = straight-line distance between two points
  sqrt(sum((ai - bi)^2)) -> sensitive to vector magnitude
Cosine similarity = angle between two vectors
  cos(theta) = (A dot B) / (||A|| * ||B||) -> only cares about direction

For text embeddings, cosine similarity is preferred because it's
insensitive to document length (magnitude).

FAISS IndexFlatL2 uses Euclidean distance by default, but with
normalized embeddings (which BGE produces), L2 distance and
cosine similarity are equivalent.


Q99. How does semantic search work?
───────────────────────────────────
1. Convert query text -> 384-dim vector using same embedding model
2. Search FAISS index for nearest neighbors
3. Return chunks whose vectors are closest to the query vector
4. "Closest" = smallest Euclidean distance (or largest cosine similarity)


What is FAISS?
──────────────
Facebook AI Similarity Search. An open-source library for efficient
similarity search in high-dimensional vector spaces.

From rag_pipeline.py:
  import faiss
  self.index = faiss.read_index(FAISS_INDEX_PATH)
  distances, indices = self.index.search(query_embedding, search_k)


Q101-Q105. FAISS Details
────────────────────────
Why FAISS: Fast (sub-ms), local, GPU-capable, memory-efficient, battle-tested.
Our index is ~1 GB.

How it works: IndexFlatL2 (exact brute-force search):
  Compute L2 distance between query and every stored vector
  Return k vectors with smallest distances
  O(n * d) where n = vector count, d = 384

We use IndexFlatL2 (exact search, no approximation). Appropriate for
our scale (<1M vectors). For >1M, switch to IVF or HNSW.


Q106. Why vector search instead of SQL LIKE?
───────────────────────────────────────────
SQL LIKE '%liabilities%' only finds the exact word "liabilities".
Vector search finds: "debts", "amounts owed", "financial obligations",
"outstanding balances" -- all semantically similar.

──────────────────────────
K values in our app:
  Default k=5 for general queries
  k=10 for risk analysis and synergy scoring
  k=15 for deep key risk analysis

Too small: Missing context
Too large: Irrelevant chunks dilute prompt, latency increases

Filtering by project:

      .select('file_name').eq('project_id', project_id).execute()

What is LoRA? - DETAILED MATHEMATICAL EXPLANATION
──────────────────────────────────────────────────
LoRA = Low-Rank Adaptation of Large Language Models

THE PROBLEM:
Fine-tuning a full 8B parameter model requires:
  8B x 4 bytes (FP32) = 32 GB just for model weights
  32 GB for gradients
  32 GB for optimizer states (Adam)
  = ~96 GB GPU memory -- impossible on consumer hardware

THE LoRA SOLUTION:
Instead of updating all 8B parameters, LoRA:
1. FREEZES all original model weights (no gradient computation)
2. Injects small trainable "adapter" matrices into attention layers
3. Uses low-rank decomposition: delta_W = A x B
   where A is (d x r) and B is (r x d), and r << d

THE MATHEMATICS:
  Original weight matrix W in R^(d x d) where d = 4096
  Full fine-tune: Update all d^2 = 16.7M parameters per layer
  LoRA: Add delta_W = A x B where A in R^(d x r), B in R^(r x d)
  With r = 16: Only 2 * d * r = 2 * 4096 * 16 = 131,072 params per layer
  Reduction: 131K vs 16.7M = 128x fewer parameters!

  During forward pass:
    output = W*x + alpha*(A*B)*x    (alpha = scaling factor)

  During backpropagation:
    Only A and B receive gradients (W is frozen)

  Across all 32 transformer layers with attention (Q, K, V, O projections):
    Total trainable params: ~4-8M (vs 8B) = 0.1% of original model

WHY IT WORKS:
  Research shows that the weight updates during fine-tuning have low
  intrinsic dimensionality. This means the change matrix delta_W can be
  accurately approximated by a low-rank matrix A*B without significant
  information loss.

  Intuition: Fine-tuning for M&A doesn't change the model's fundamental
  language understanding. It only adjusts a few "directions" in the weight
  space to emphasize financial terminology and structured output. These
  few directions can be captured by a low-rank (r=16) matrix.

BENEFITS:
  Train on a single GPU (8-16 GB VRAM)
  Training time: hours instead of days
  Adapter files are small (~10-50 MB)
  Can swap adapters for different domains
  Original model knowledge is preserved


Q121. What is QLoRA?
────────────────────
QLoRA = Quantized LoRA

Takes LoRA further by:
1. Loading the base model in 4-bit quantization (NF4)
2. Applying LoRA adapters on top of the quantized model
3. Computing gradients in 16-bit, but storing weights in 4-bit

Memory savings:
  Full model (FP32): 32 GB
  LoRA (FP16):       16 GB
  QLoRA (4-bit):      4 GB  <- Can train on a single RTX 3060!

From our config.json:
  "quantization_config": {
      "load_in_8bit": true,
      "quant_method": "bitsandbytes"
  }

Our model uses 8-bit quantization via bitsandbytes.

      if result is not None:

      return result                        # 5. Return

Q309. Mathematics of vector similarity:
  Cosine Similarity:
    cos(theta) = (A dot B) / (||A|| * ||B||)
    Range: [-1, 1], 1 = identical

  Euclidean Distance (L2):
    d(A,B) = sqrt(sum((ai - bi)^2))
    Range: [0, infinity), 0 = identical

  With normalized vectors: d^2(A,B) = 2 - 2*cos(theta)
  Minimizing L2 distance = maximizing cosine similarity
